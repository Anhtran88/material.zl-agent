# Zalo Material Delivery Manager — Architecture

Status: design baseline; Milestone 1 read PoC accepted in a user-approved reduced scope on 2026-10-11 (see IMPLEMENTATION_PLAN.md). M2 capture-scoped candidates/review are implemented pending live acceptance. Full extraction and accounting remain unimplemented. Accuracy > traceability > integrity > automation > speed.

## Requirements and risks
Zalo is a read-only source restricted to a user-maintained Allow List. Timeline is primary; media library is recovery only. No send, reply, react, forward, edit, delete, recall or upload capability is exposed. Manual login is required; QR, CAPTCHA, logout, verification and ambiguous UI stop automation. Opening a conversation may mark messages read in Zalo; this is a platform side effect that must be disclosed during live acceptance. We cannot claim zero server writes merely from a read-only application API.

Zalo has no verified stable DOM contract in this environment. Virtualized timelines can hide messages, timestamps can be incomplete, IDs may be unstable, and expiring attachment URLs require the existing session. Selectors must be captured and verified locally; invented selectors must never be treated as production-ready. Require a uniquely matched conversation ID and exact title, then recheck identity on every read/download. Duplicate names, missing metadata, unsupported attachment types and coverage uncertainty stop rather than silently skip. Headed Playwright persistent profile is local, outside OneDrive, treated as a credential with Windows user ACLs; never export it or log cookies. No injected request blocking based solely on HTTP method: Zalo reading itself may require POST. Adapter interaction allowlisting and live network audit provide the controls, with limitations recorded.

## Components and folders
Python agent + Playwright adapter; later FastAPI loopback API, React/TypeScript UI, Firebase Auth, Cloud Firestore persistence, Firebase Storage and an authenticated cloud ingestion backend. Separate ports: ZaloAdapter, OCRProvider, AIProvider/AIModelRouter, FileStore. Deterministic parsers precede OCR/AI. Configurable OpenAI-compatible 9Router gateway only after real API compatibility verification. Secrets via Windows Credential Manager. No frontend service-account or provider secrets. Firebase client config is public configuration, not an authorization boundary.

```

config/              selector contract example

 tests/              unit, adapter contract, later browser fixtures
```

Future packages: bundle, duplicate, jobs, extraction, validation, pdf, storage, reports, api; frontend separately. Authoritative business data resides in Cloud Firestore; images/PDFs and large evidence objects reside in private Firebase Storage. No local business database, capture JSON, business logs, persistent offline cache or OneDrive archive. `%LOCALAPPDATA%/ZaloMaterialAgent` remains only for the Zalo credential profile, bridge/9Router credentials and installed runtime dependencies. Current Local Agent reads are memory-only previews until cloud setup and ingestion are implemented; no cloud commit is claimed.

## Database schema
See schemas/firestore.md and firebase/ for the new authoritative schema and locked deployment scaffold. schema.sql is a historical relational reference, not the target or an active migration. Tenant-scoped IDs/references, immutable evidence revisions, decimal strings and date-only confirmation fields remain. Firebase Auth scopes user/device access; no service-account key is distributed to desktop/mobile clients. Multi-device realtime listeners operate on bounded tenant-scoped cloud queries; business transitions pass through validated backend transactions.

## Agent state machine
IDLE -> OPENING -> WAITING_LOGIN -> READY -> RESOLVING_SOURCE -> READING -> GROUPING -> DOWNLOADING -> HASHING -> EXTRACTING -> CROSS_CHECKING -> VALIDATING -> BUILDING_PDF -> PREPARED -> COMMITTING -> PUBLISHING -> CHECKPOINTING -> ARCHIVING -> CLEANING -> COMPLETED.
Any step may enter PAUSED_USER (login/security/uncertainty), NEEDS_REVIEW (business conflict), RETRY_WAIT (transient error), FAILED (exhausted retries) or CANCELLED. M1 stops after READING/DOWNLOADING and logs evidence; no business completion/checkpoint. Persistent jobs later have attempt count, next retry, lease expiry, owner and state version; compare-and-swap transitions, bounded exponential retry with jitter. Expired leases recover by inspecting durable artifacts, not replaying side effects blindly.

## Delivery Bundle Engine (M2)
Read overlapping bounded chronological windows from one conversation, retaining ordering, sender, IDs, timestamps, text and attachment metadata. Generate candidates in both temporal directions; attachment-before-description, description-before-attachment and follow-up supported. A time window alone never proves membership. Hard reject cross-conversation candidates; incompatible explicit slip/project/date signals require review. Score independent available evidence: sender, proximity/order, material, project/location, supplier, document number, quantities, OCR content. Record each contribution, missing evidence, model/ruleset version and candidate alternatives. Initial metadata scoring precedes selective download; OCR then refines without allowing an uncertain merge to silently become committed.

Defaults >=.90 eligible for auto-processing, .70–.89 process provisionally with warning/review, <.70 review without accounting. Thresholds configurable and calibrated on labeled test data; heuristic score is not a statistical probability. Weak temporal-only evidence has a confidence cap below auto threshold. Competing candidates or hard conflicts always override the score. Human split/merge/approval creates audited revisions. Late attachments update the existing bundle revision when supported by evidence; no new accounting event by default.

## Five duplicate layers
1. Source message ID, else versioned canonical fingerprint (conversation, exact normalized Unicode text, stable sender/time and attachment identity). Preserve raw values. Ambiguous identical messages retained for review.
2. Source attachment identity and association, never filename.
3. SHA-256 binary identity with immutable FileRecord; reuse bytes but keep every provenance link.
4. Bundle revision fingerprint of sorted stable evidence IDs and content hashes; late evidence changes revision, not BundleID.
5. Business candidate key: document number/date/project/supplier/material/unit/quantities. Different photos can share business identity. POSSIBLE_DUPLICATE blocks automatic accounting until reviewed; a match alone is not proof.

## Checkpoint and resume (M3)
Separate scanned cursor from finalized cursor. Capture raw evidence atomically before moving scanned cursor. Final cursor only reaches the highest contiguous safely terminal segment (committed/published evidence or explicitly audited non-delivery decision); review, failed download and unresolved holes block it. Processed membership tables track messages, attachments and bundle revisions. Resume jobs first, then scan bounded overlap by stable cursor/time plus seen IDs. Timestamp alone cannot define ordering. No stable cursor or uncertain virtualized coverage => pause/backfill explicitly; never claim complete history. Out-of-order/late events trigger periodic bounded lookback with duplicate checks; edits require evidence revision and review.

## Validation and evidence
Keep separate message_timestamp, chat_stated_date, delivery_note_date, weighing_note_date, document_date and confirmed_delivery_date; every extracted date links evidence. Conflict => DATE_CONFLICT/review, never choose message date. Separate requested/ordered/delivered/received/accepted/returned amounts, unit and document role. Preserve original strings, parse Vietnamese separators explicitly, reject ambiguity. Decimal arithmetic calculates deltas, including unit validation; no LLM arithmetic. Each important field links document/page/location or message span, method and confidence. Validate dates, project, material, slip, supplier, units, missing evidence and duplicate against chat/documents/DB. Reports include only verified current accounting revision. Null is not zero.

## Transaction boundary and publication saga
Firestore and Firebase Storage cannot commit atomically together. Use authenticated, idempotent cloud capture manifests and immutable Storage generations. PREPARED/outbox transaction records intent without accounting activation; verified cloud artifacts allow a second transaction to activate one bundle revision and advance only eligible checkpoints. Server-owned leases plus fencing tokens stop stale devices from committing. Recovery reconciles object generations/manifests and retries stable idempotency keys. No local persistent outbox: disconnected agents pause, bounded unacknowledged RAM data can be lost on shutdown, and no durable-success response is emitted. Cloud backups/retention replace SQLite/OneDrive copies. Details and schema limits are in schemas/firestore.md.

## Test strategy
M1 contract tests plus a real headed-browser dataset under an explicit Allow List. Include duplicate group titles, identity changes, security challenge, missing/changed selector, mixed image/PDF/Word/Excel attachments, download timeout and corrupt bytes. Compare expected message/attachment counts and SHA-256 manifest. Static absence of forbidden methods is supplementary, not proof of live read-only behavior. Audit every permitted interaction; inspect browser/network activity locally without exporting credentials. Later milestones test all prompt scenarios: grouping in both directions, late attachments, replay/restart, different-photo business duplicate, conflicting dates, Decimal deltas, evidence clicks, valid PDFs, collision-safe filenames, outbox crash injection and OneDrive failure. Gate each milestone with a recorded acceptance report; no next milestone while required evidence is missing.

## User-requested Local Agent/MCP/9Router connection extension
See docs/LOCAL_AGENT.md. Loopback-only HTTP Local Agent with random expiring bearer credential, Windows DPAPI, explicit local read enable, serialized bounded DOM operations and revocation. Local stdio MCP forwards five fixed operations; no arbitrary execution, selectors, clicks, remote tunnel or whole desktop API. Existing cloud chat cannot dynamically attach this local server. Pinned standalone 9Router bootstrap owns its subprocess/data/credentials, uses reviewed management APIs, requires provider approval, and verifies models endpoint without source/completion requests. It does not advance bundle/extraction milestones. Captures remain RAW and incomplete until live timeline identity/sender/time/attachment coverage is proven. Read/AI actions have no business transaction or final checkpoint.

## User-approved scope revision — 2026-10-11
The user waived complete history, sender/message-time completeness and original attachment download/hash as M1 acceptance blockers. Primary business evidence is message content and the confirmation calendar date explicitly shown on a delivery slip (day/month/year only). Preserve that field and its provenance independently; the business field has no time component, even if the slip also prints a clock time. Missing or conflicting slip confirmation values remain unknown/reviewable, with no substitution from chat timestamps or DOM IDs. These waivers permit the reduced read PoC acceptance; they do not assert that document extraction already works or change later publication/archive integrity requirements. Allowlisting, read-only behavior, manual authentication and safe checkpoint/accounting rules remain in force.

## Message and confirmation-date contract
Retain the original full message body alongside structured fields: stated dates, material/specification, project/location, each quantity and unit, and additional references/notes. Multiple entries must retain their associations and source spans, with ambiguity flagged rather than silently merged. Truncated captures are explicitly incomplete. A slip confirmation date is date-only, normalized to YYYY-MM-DD after validation and displayed as DD/MM/YYYY, with the original string and page/location evidence retained. Keep it separate from other document dates and message-stated dates; neither chat time nor a DOM identifier supplies this field. This is the extraction contract, not a claim that OCR/extraction is already implemented.

## Cloud persistence revision — 2026-10-11
User requested cloud-only business persistence and future realtime multi-device clients. Cloud Firestore is chosen over Realtime Database for structured evidence, queries and transactional business state; Firebase Storage holds binary artifacts. No Firebase project exists yet. Deployment and actual authenticated ingestion/listeners remain pending project creation and access. Bootstrap rules deny all client access until tested tenant membership rules/backend exist. Legacy PoC/standalone inspector file-export entrypoints are disabled under this policy; historical implementation tests do not establish cloud persistence. Previous local cache files are not deleted automatically.

## M2 implementation mapping
Current Engine is a conservative DOM-order candidate/review implementation (bundle_engine.py), not OCR-based automatic grouping. It preserves full message text, optional display metadata and provisional source/evidence IDs. Local operator per-image assignment and direct message merge/split create immutable capture-scoped reviewed snapshots, with no business completion. RAW capture and bundle draft revisions are atomically created in Firestore; queryable revision metadata accompanies proposalJson. Current scoring stays below automatic thresholds because actual document content is unavailable. Cross-capture uniqueness, durable jobs/leases, reopening cloud review and multi-device transactions remain M3/cloud foundation. See docs/MILESTONE_2_REPORT.md; M2 live acceptance is pending.

## M3 implementation mapping — 2026-10-11
RecoverableFirestoreStore is now the default read/review port. Canonical exact-capture identities, source-scoped observation signatures, durable cloud PREPARED jobs/chunks and attempt limits, server-read-time leases with updateTime fencing, and atomic capture/bundle/checkpoint completion support restart and cooperative-device recovery. Resume restores the last durable capture without reading Zalo or storing business files locally. Checkpoint pointer/capture sequence is separate from unchanged scanned/finalized historical/business cursors. Binary and business identities require later actual evidence; no false verification/duplicate accounting claim. Public-rule security limits and detailed fault-test evidence are in docs/MILESTONE_3_REPORT.md; live acceptance is pending. M2 manual-review gate was waived by the user, but associations remain unverified.

### Automatic monitoring extension

Local-only authenticated Play restores the latest durable Firestore capture and starts one serialized backend worker. It verifies the allowed source before every DOM operation, derives a unique conversation scroller from verified source containers, moves to the bottom, and performs bounded backward catch-up to the last saved opaque DOM container when necessary. It returns to the bottom before saving. Comparison excludes rendered-order-only changes, retains complete message text and detects new/changed observed metadata. Each successful change uses the recoverable Firestore ingestion path; unchanged polling does not create a capture. Pause drains current work; source/UI/cloud failure, disconnect, shutdown or the 8-hour control-session expiry stops monitoring. Active Play re-verifies and renews the 30-minute source connection. No automatic business acceptance, parsed slip date or stable server identity is inferred.

### User-configured multiple sources

A cloud registry at `tenants/default/settings/zaloGroups` stores normalized authorized names, stable configuration IDs, selected checkboxes and verified candidate DOM group bindings using CAS. Existing single-source paths remain compatible; source-specific store instances derive lease/checkpoint keys from each group ID. An authenticated local operator may add names or select multiple groups. The worker serializes group selection, source verification, recovery, bounded incremental reading and save; it switches only exact-title approved conversation rows, with bounded sidebar scrolling. Unknown IDs are bound after successful browser verification and cannot silently replace an existing binding. Source provenance remains internal to cloud records while the UI displays a shared summary.
